# Experimental design: what is `.fsf` in Software Heritage?

*A second application of the extension-study playbook
(`docs/swh_extension_study_playbook.md`), on a **non-programming** extension.*

## 1. What `.fsf` is (evidence)

`.fsf` is the **FSL FEAT design file** — the configuration format for *FEAT*
(fMRI Expert Analysis Tool) in the **FMRIB Software Library**, the dominant
open-source fMRI neuroimaging analysis suite. It is a **Tcl `set`-variable
config**, usually auto-generated by the FEAT GUI and heavily self-documented.
A fetched sample begins:

```tcl
# FEAT version number
set fmri(version) 3.14
# Are we in MELODIC?
set fmri(inmelodic) 1
# Analysis level   1: First-level   2: Higher-level
set fmri(level) 1
set fmri(analysis) 7
set fmri(outputdir) "..."
```

Filename evidence (from `fsf_files.csv`, 22,901 rows): `design.fsf` (4,270),
`*_run-*_level.fsf`, `feat_level_func*.fsf`, `*.fmri.taskFT.run.melodicFixNone_design.fsf`,
BIDS `sub-*_run-*` naming — all FEAT/fMRI. Provenance (`fsf_files+origin.csv`):
22,898/22,900 have an origin, across **757 distinct origins**; forges led by
`github.com` (20,688) and **`git.mpib-berlin.mpg.de`** (Max Planck Institute,
1,206) — a strong neuroscience signal.

**So `.fsf` is not a programming language** — it is a domain-specific
*configuration* format. In the project's own vocabulary
(`docs/extension_labels.md`) the likely correct label is `data:config` /
`data:domain` (neuroimaging), **not** `pl/*`. That makes `.fsf` an ideal
control case: a well-defined non-PL, to check the method doesn't hallucinate a
language.

## 2. Why this case is worth running

- **Method validation (negative case).** COBOL proved the pipeline on a real
  PL with contamination. `.fsf` proves it correctly identifies a *non-PL config
  format* and resists the temptation to call Tcl-syntax "a programming
  language". If the judge says `is_programming_language = false,
  artifact_kind = fsl-feat-design`, the method generalises.
- **Extreme duplication → the by-file/by-repo lesson, amplified.** FEAT
  auto-generates one `.fsf` per subject × run × analysis level, so a single
  study can emit thousands of near-identical files. 22,900 files but only 757
  origins (≈30 files/repo, heavily skewed). By-repo sampling is essential here.
- **A different contamination question.** Does `.fsf` collide with anything
  else (as `.cbl` did with comic books)? Candidates to test, not assume:
  FontForge/other tools, or hand-written non-FEAT Tcl. Measure it.
- **Feeds the extension mapping** with a concrete `data:config` label +
  provenance for a 22.9k-file extension currently unclassified.

## 3. Research questions (hypotheses to test, not assume)

- **Q1 — Is it a PL?** *H1: no* — a domain config/DSL. Expected label
  `data:config` (neuroimaging). Success = judge says not-a-PL with high
  confidence and correct positive identification.
- **Q2 — What is it, precisely?** FEAT version distribution; **first-level vs
  higher-level** (`set fmri(level)`); **task-GLM vs resting-state/MELODIC-ICA**
  (`set fmri(inmelodic)`, EV count); registration-only; GUI-generated vs
  hand-edited.
- **Q3 — Contamination.** What fraction of `.fsf` is *not* FEAT? (non-FEAT Tcl,
  other tools, data, docs, binary.)
- **Q4 — Population & provenance.** by-file vs by-repo distributions;
  duplication factor (files per distinct study); forge/lab concentration (how
  much is Max Planck / large consortia); how many distinct *studies* (~757
  origins) vs files.
- **Q5 — Method.** Does the generalized pipeline label a non-PL correctly, and
  does a cheap reclassifier match the LLM on "is this FEAT"?

## 4. Pipeline adaptations

### 4.1 Indicators (`indicators_fsf`)
Deterministic, from bytes:
- lines; comment lines (`^#`); **comment ratio** (FEAT files are ~50 % comment);
- count of `set fmri(...)` directives; `set feat_files(...)`,
  `set highres_files`, `set fmri(evN...)`;
- `set fmri(level)` value (1/2); `set fmri(inmelodic)` (0/1);
  `set fmri(analysis)`; **number of EVs** (`set fmri(evs_orig)` / `evs_real`);
- FEAT `version`; presence of absolute paths / subject IDs;
- `is_tcl_set` (does it look like `set var value` throughout?);
- `is_feat` = has ≥1 `set fmri(`. (This is the natural **gate**.)

### 4.2 LLM-judge taxonomy (`taxonomy_fsf`) — enum-constrained
```
is_programming_language : bool            # expected false
artifact_kind : { fsl-feat-design, fsl-melodic-config, tcl-script,
                  config-other, data, docs, binary, other }
feat_level    : { first-level, higher-level, not-applicable, unknown }
analysis_type : { task-glm, resting-state-ica, registration-only,
                  group-stats, unknown }
generated     : { gui-generated, hand-edited, unknown }
domain        : { neuroimaging-fmri, other, unknown }
not_fsf_label : { none, data, docs, other-format, binary }   # if not FEAT
feat_version  : free-text ; n_evs : int ; summary/detail : free-text
confidence    : { high, medium, low }
```
Prompt shows the mechanical indicators (as with COBOL) so the judge is anchored
to the same evidence.

### 4.3 Reclassifier (`reclassify_fsf`) — zero-API, bootstrapped from the judge
Content-rule categories:
- `fsl-feat` — contains `set fmri(` (strong, near-certain);
- `tcl-other` — `set var value` syntax but no `fmri(`;
- `config-other`, `data`, `binary`, `other`.
Validate against the judge on a tail sample (aim P/R/F1 as with COBOL).
Because `set fmri(` is a near-perfect marker, expect **very high** precision
and recall here (a cleaner target than COBOL) — a useful contrast.

### 4.4 Gate
`is_feat` (has `set fmri(`) — skip the judge on non-FEAT files only if you want
to save spend; but `.fsf` files are small (config), so **judging all is cheap**
and lets us measure contamination directly. Recommend: judge all (no gate) for
the population sweep; gate only if scaling far.

### 4.5 Sampling (two frames)
- **Uniform-random N=1,000** over the 22,900 contents → the *file* population
  (dominated by auto-generated per-subject designs).
- **Origin-diverse N≈757** (≤1 file per origin — the pool only has 757
  origins) → the *study* population (one design per project).
Compare, exactly as COBOL by-file vs by-repo. Expect a large duplication gap.

## 5. Experimental plan (mirrors COBOL)

1. `sample` uniform N=1000 (seed) and `sample_diverse` (all 757 origins).
2. `run_study --no-judge` → fetch (cached) + fsf indicators. *(~1000 + ~757
   fetches; anon 120/h ⇒ background/self-pacing, or a token.)*
3. `run_study --judge` with the fsf schema (no gate for the 1k population sweep).
4. `reclassify_fsf` + `eval_reclassify` (validate vs judge on a tail sample).
5. `origins` from `fsf_files+origin.csv` (already present) → by-repo sample +
   concentration + forge/lab breakdown.
6. `review_app` (generalised) for human spot-checks of any judge/reclassifier
   disagreements and of the suspected non-FEAT tail.
7. Figures + write-up: contamination, FEAT sub-types, by-file vs by-repo,
   duplication factor, provenance.

## 6. What would validate the method

- Judge says **`is_programming_language = false`** for ~all real `.fsf`, with
  `artifact_kind = fsl-feat-design` and `domain = neuroimaging-fmri` — i.e. it
  *correctly declines to call it a language* and *correctly names it*.
- Reclassifier (`set fmri(` marker) matches the judge with **F1 ≳ 0.95** on
  "is FEAT" (a cleaner marker than COBOL divisions).
- A measurable **by-file vs by-repo gap** (e.g. first-level task designs
  dominate files; by-repo reveals the spread of study types).
- A named contamination tail, if any (the `.fsf`-collision analogue of comic
  books).

## 7. Cost & effort

- **Fetch:** ~1,000 (uniform) + up to 757 (diverse), deduped ⇒ ≈1,500 unique
  fetches. Anon ≈120/h → ~12 h background (self-pacing), or ~30 min with an
  `SWH_TOKEN`.
- **Judge:** `.fsf` files are small; ~1,500 × ~$0.01 ≈ **$10–15**.
- **Build:** ~a day to parameterise `taxonomy_fsf`, `indicators_fsf`,
  `reclassify_fsf`, `judge` schema. The rest of `tools/cobol/` is reused (a
  future refactor could make the toolkit take an `--ext`/profile argument so
  COBOL and fsf share one codebase).

## 8. Expected story (to be confirmed, not assumed)

`.fsf` on SWH is almost entirely **FSL FEAT fMRI designs**, overwhelmingly
**first-level, GUI-generated**, with massive **auto-generation duplication**
(22.9k files ⇢ ~757 studies), concentrated on GitHub + a few neuroscience labs
(Max Planck). It is **not a programming language** — the method should label it
`data:config` (neuroimaging) and quantify the FEAT sub-types and the small
non-FEAT tail. If so, the extension-study approach is demonstrated to work
symmetrically on *both* a real PL (COBOL) and a non-PL domain format (`.fsf`).
